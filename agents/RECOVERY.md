# Bad-code recovery

## Before merge

The builder pushes to an issue branch, never to the default branch. `Agent PR` CI runs `product-check.sh`; once the ingest adapter exists, it also runs the factory-owned black-box checks from the default branch. A failed or missing check prevents reviewer dispatch. The reviewer examines the diff and can request changes. The tester runs issue-specific acceptance checks and can file a bug. Either rejection returns the issue to the builder. The builder fixes the same PR with a new commit, preserving the failed attempt in history. Review and test verdicts must name the current head SHA. The queue posts a required `factory-gates` commit status as pending until both verdicts pass, or as failed when either gate rejects. The poller blocks a fourth builder dispatch by default for human investigation. Before merging, the human runs `bash agents/merge-check.sh ISSUE_NUMBER` and inspects the PR.

## After merge or deployment

Stop the product service or disable its public Run now trigger if the bad release could corrupt data or burn model quota. Run `bash agents/release-product.sh rollback` to restore the previous successful merged revision and run its smoke check. The release script also restores the prior revision automatically when a new deployment fails its smoke check. It keeps the persistent data directory outside release code and never deletes it. Do not reset or delete run history to hide a failure. Open a linked bug issue, ask a builder for a fix or revert PR, and put that PR through CI, review, and test before the human merges it. Record the bad revision, rollback revision, observed failure, and fix in the ticket and `DELIVERY.md`.

The builder must add `product-service.sh` to the product repository. It receives one argument: `prepare`, `restart`, or `smoke`. The release script exports `BRIEFING_CURRENT_DIR`, `BRIEFING_DATA_DIR`, and `BRIEFING_RELEASE_ROOT`. `prepare` installs free runtime dependencies for the release without modifying persistent data destructively. `restart` starts or restarts the product from `BRIEFING_CURRENT_DIR`; `smoke` checks the actual public briefing URL and returns nonzero when it fails. These adapter commands cannot be tested against the product until the agents build it. The deployment ticket must implement and exercise them before a live submission.
