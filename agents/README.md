# Delivery team

| Agent | Runtime | Role | Model variable |
| --- | --- | --- | --- |
| manager | Hermes profile | Orchestrator and ticket owner | `OPENROUTER_REASONING_MODEL` (`:free`) |
| ingest | OpenClaw agent | Feed, persistence, deduplication builder | `OLLAMA_MODEL` |
| page | OpenClaw agent | Public page and deployment/ops builder | `OLLAMA_MODEL` |
| reviewer | Hermes profile | Independent PR reviewer | `OPENROUTER_REASONING_MODEL` (`:free`) |
| tester | Hermes profile | Independent acceptance tester | `OLLAMA_MODEL` |

The default `python agents/setup/apply.py` path creates the AWS EC2 VM, installs the runtimes, enables the queue, and dispatches the manager with the tracked spec selected by Terraform `spec_path`. In manual mode, run `agents/dispatch.sh manager` after setup. The manager creates GitHub Issues and labels ready builder tickets. A systemd timer polls GitHub every two minutes and dispatches one labeled ticket at a time. Each dispatcher invocation loads the issue and comments and runs the named runtime. Builders open PRs; the `Agent PR` GitHub Actions workflow runs the builder-maintained `product-check.sh` tests. Factory-only setup PRs run the factory checks without a product-check.sh; builder PRs must provide product-check.sh. The queue waits for passing CI before handing a builder PR to reviewer. Reviewer can request changes; tester can open a bug and return the ticket to a builder. Both verdicts name the current PR head SHA. The human owner runs `bash agents/merge-check.sh ISSUE_NUMBER`, reviews, and merges only after review and test sign-off. See [RECOVERY.md](RECOVERY.md) for the bad-code path.

The manager plans in its foreground Hermes run. Hermes `delegate_task` is deliberately unused because a background child can overlap the parent on the shared one-request Ollama key. Profile switching and cross-runtime execution happen through the queue and dispatcher.

The `agents/` prompts are role instructions. They do not implement the product. Manager and reviewer use the strong OpenRouter `:free` reasoning model; ingest, page, and tester use Ollama Beam. The issue poller, startup dispatch, and `manager-chat.sh` share a filesystem lock for the one-request Ollama tier; direct model calls from the dashboards or an unwrapped CLI command bypass that cross-runtime lock, so do not use those during a factory run. Beam roles fall back to a configured OpenRouter `:free` model, and the manager/reviewer fall back to Beam. Record whether a fallback actually succeeded after HTTP 402/429. Never claim a fallback was tested until a real call succeeds.

After every dispatch, the dispatcher writes one `.local-evidence/usage/RUN_ID.activity.json` with agent, issue, source stage, attempt, work phase, actual reported model, token total, measurement method, and raw usage filename. It posts a short `ACTIVITY:` comment on the issue after the run; startup runs without an issue remain in the private ledger. It also keeps Hermes `--usage-file` JSON or OpenClaw `agent --json` output. Run `bash agents/usage-report.sh` for per-run and agent/model/phase totals. The first dispatch for an agent and issue is classified as planning, coding, or review/test by role; repeats for that same pair are classified as retries. Missing usage stays unknown, never zero. If a runtime omits usage, add a documented estimate with `python3 agents/activity.py estimate --usage-dir .local-evidence/usage --run-id RUN_ID --model PROVIDER/MODEL --tokens COUNT --method 'source and calculation'`. Hermes totals include auxiliary calls; the summary puts them under an unknown model when attribution is unavailable. Use the activity records, issue/PR trail, and plain words about where tokens went in `DELIVERY.md`. Do not commit `.local-evidence/` or credentials.

After the agents have created tickets, run `python3 agents/trace-report.py --output .local-evidence/trace-excerpts.md` on the authenticated VM checkout. It extracts a few exact `HANDOFF:` comments and a real `REVIEW: CHANGES REQUESTED`, `TEST: FAILED`, or retry `ACTIVITY:` comment, with timestamps and links to the source issue comments. Review the generated file, then copy appropriate excerpts into `DELIVERY.md`. If no rejection or retry occurred, the report says so; never fabricate one. The extractor includes only comments by the authenticated GitHub identity used for agent dispatch.

## Before dispatch

Run `gh auth login` and `gh auth setup-git` on the VM, then verify `gh repo view` and that the checkout has an `origin` remote. Give the VM's GitHub identity permission to create issues and PRs. Agents use explicit git author names in their commits; the PR and issue comments show the actual GitHub account used. Do not invent separate GitHub identities.
The dispatcher accepts issue bodies and comments only from that authenticated GitHub identity; the manager must create the routed issues from the VM's account. This keeps public issue comments from becoming agent instructions.

Run `bash agents/enable-queue.sh` after GitHub authentication. Create native issue dependencies with `bash agents/link-dependency.sh DEPENDENT_ISSUE BLOCKING_ISSUE` for every prerequisite. The dependent issue enters `briefing:waiting`; the poller releases it when every blocker issue is closed and every blocker builder PR is merged. A manually set `briefing:ready` label on a blocked issue is returned to waiting. The queue recognizes `briefing:ready` with `agent:ingest` or `agent:page`; it moves an open builder PR with the required fields to `briefing:review`, waits for passing `Agent PR` CI, then requires reviewer and tester verdicts for the same head SHA before `briefing:merge-ready`. A stale or conflicting PR is returned to its builder for an updated commit; review and test repeat. Other failures route to `briefing:needs-manager`; the manager must record a `MANAGER:` decision and choose one next-stage label. A manager failure ends at `briefing:blocked`. After human merge the queue closes any still-open issue and marks it `briefing:done`. Check `journalctl --user -u briefing-issue-poller.service` and `systemctl --user list-timers briefing-issue-poller.timer` to observe it.

For an OpenClaw workspace, `AGENTS.md` is copied into its isolated workspace. For Hermes, `SOUL.md` is copied into its profile. The repository copies remain the reviewable source of those instructions.

## Repository hardening after publication

The queue posts `factory-gates` as pending when a builder hands off a new PR head, failure after a review/test rejection, and success only after both gates pass for that same head. Branch protection should require both this status and the `verify` CI check; a new push has no success status until the gates run again.

The default Terraform preflight applies and verifies branch protection with the local repository owner's GitHub CLI before VM creation. Run `bash agents/protect-repo.sh` yourself after a later protection change or in manual setup. It requires PRs, `verify`, and `factory-gates` on the default branch, includes admins, and blocks force pushes. GitHub Free supports this on public repositories; a private repository needs an eligible paid plan. Builder PRs that change factory-owned workflow, queue, infrastructure, or acceptance files are routed to the manager; make those changes as a separate human-reviewed setup update. The reviewer and tester currently share the VM's GitHub login with builders, so their issue comments are inspectable evidence, not independent GitHub approval identities. This owner account cannot approve its own PRs; branch protection requires zero native approvals while still requiring PRs and both status checks. Keep the human merge decision. Add a separate reviewer account or GitHub App only if you need GitHub-native approval enforcement. Once the product stack is chosen, add its formatter/linter and dependency or secret scanning to `product-check.sh`. The factory-owned black-box tests under `factory-tests/` exercise the ingest code after the stable-ID adapter is added. The local `merge-check.sh` is an additional pre-merge check, not a substitute for server-side branch protection.
